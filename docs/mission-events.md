# API mission events (pure observer)

The journal records witnessed transitions from `ModApi.Services.Missions.Transitioned` only. It installs no Harmony patches and carries no compile-time `Assembly-CSharp` reference; there is no direct-hook fallback mode. `MissionJournal` requires VGModAPI **0.2.8+** via a hard `BepInDependency` (the loader gate is authoritative; there is deliberately no exact-minor upper gate). At startup the journal requires the mission service and its `IdentityContinuity` view, plus lifecycle `SessionTracking` and `SaveOutcomes`, to report typed availability; an unavailable service stops initialization with the `Reason`/`Detail` diagnostics in the log rather than degrading silently.

Accepted records use the API occurrence GUID (`MissionSnapshot.InstanceId`). Repeated definitions stay separate. Completion, failure and abandonment reflect the API's witnessed outcomes, not successful method returns. Neutral removal creates a `Removed` terminal timeline entry with no claimed outcome; it is neither failure nor abandonment. Archive notifications do not invent completion or duplicate its timeline entry. Unknown transition enum values from newer producers are logged and ignored, never fatal.

The journal remains **acceptance-first history**. Restoration does not create an Accepted entry. A later outcome updates a saved record only when its exact occurrence GUID exists. Missing or ambiguous correspondence (`MissionIdentityEvidence.MissingOrAmbiguous`/`Unavailable`), old imported history with unrelated IDs, and evicted acceptance records cannot be matched by name, definition or ordinal. Such outcomes are logged as missing acceptance history and omitted rather than manufacturing a timestamp or acceptance event. Existing imported history remains intact and queryable. An active journal record means no terminal event was recorded, not proof of present vanilla membership; ambiguous correspondence can leave an unresolved historical record. `Restored` events need no deferred write: the saved record is looked up when a later outcome arrives, after save-data restoration.

Native mission details (steps/objectives/rewards/source placement) are inspected only during the exact API callback via the explicitly version-sensitive `IVersionSensitiveMissionAccess` escape hatch and immediately copied out by the record builder using name-based reflection (`VanillaReflection`). Native objects are not retained or mutated, and the plugin assembly never references the game assembly — inaccessible members degrade to null/empty fields rather than faulting the observer. Name and definition identity always come from the immutable event snapshot, never the native view. Structural/reward details from the version-sensitive native view can reflect later nested mutations.

Unavailable save data prevents recording (the live `ISaveDataRegistration.CanMutate` gate plus observer health). Inspection errors stop the observer and immediately dispose its save-data registration, protecting against publication of incomplete history. Owner disposal pauses shared saving until a fresh session; restart is required to reinitialize the journal observer. These controls do not claim full runtime qualification.

The payload shape remains JournalSchema 3; `Removed` is an additional timeline state. Existing acceptance/outcome records and their identifiers are not rewritten. Older journal releases cannot read the new `Removed` string state; do not downgrade a journal reader after recording it. API-managed save data is the default: the journal registers a `PersistenceProvider` (owner `vgmissionjournal`, schema 1, bounded gzip `VGJ1` payload) through `ModApi.Services.SaveData.Register`. A refusal (`SessionAlreadyStarted`, `DuplicateProvider`, `LimitExceeded`, `InvalidProvider`, `Unavailable`) is reported with its status and detail and disables the journal; it never silently falls back to file writes. Setting `[Persistence] UseApiSaveData = false` opts back into the legacy file mode, whose journal sidecars are written only on matching-session `SaveSucceeded` observations from `ILifecycleService.Changed`.

`[Persistence] ImportLegacySidecars = true` separately opts into read-only adoption of a pre-existing legacy sidecar when the API has no journal data for this save; sources are never modified, and no historical snapshot matching is inferred.
